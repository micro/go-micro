Status: design proposal, September 2026. This describes a direction and release
criteria, not shipped APIs or a committed release date.

## The evolution

Go Micro's foundation is service communication: RPC, discovery, encoding,
transport, and pub/sub, with pluggable storage and infrastructure. Agents extend
that foundation by discovering service capabilities and choosing how to use them.

The proposed next step is **a framework for applications built from services and
agents**. A developer can write an application or ask an agent to build it, then
run, inspect, revise, and recover it through the same contracts. Existing RPC
applications remain first-class; adopting AI is optional.

An app can provide a UI, a callable capability, or both. App generation is one
use of the framework. The framework also needs to make the resulting software
understandable and operable after the generating conversation ends.

## Responsibilities

| Component | Owns | Does not own |
|-----------|------|--------------|
| `service` | Capability contracts, operations, application data | Choosing a user's goal |
| `model` | Provider requests, responses, tool-call descriptions, usage | Executing tools or deciding when work is complete |
| `agent` | Model/tool execution, memory, limits, approval and continuation | App hosting or a product's account model |
| `flow` | Defined steps, verification and recovery boundaries | A second agent implementation |
| Proposed `app` | Application identity, revisions, resources and dependency contracts | Model prompting, billing or a particular hosting platform |

The model/agent split in this table is a **v7 target**. In v6, providers with a
`ToolHandler` execute tools inside `Generate`. Removing that behavior is a public
contract change and needs an explicit migration.

## First: compatible v6 cleanup

1. Share duplicated protocol code and preserve history, model options, tools,
   and errors consistently. The first change consolidates the compatible
   OpenAI, Groq, Mistral, Together and MiniMax generation loops. Other provider
   protocols and CLI orchestration remain separate at this stage.
2. Define provider conformance for one model turn: structured tool calls and
   results, provider continuation data, streaming events, usage, and stop reasons.
   Provider-specific reasoning state must survive the common representation.
3. Bring CLI chat and registered-agent execution onto the same harness, keeping
   generation as an explicitly supplied tool. Keep routing and terminal rendering
   at the CLI boundary.
4. Make work completion, limit exhaustion, cancellation, approval pauses, and
   recoverable failures explicit. A reply or a saved checkpoint alone does not
   establish that the requested effect occurred.

These changes should ship incrementally where the v6 contract can be preserved.
A major-version number is not needed for deduplication or bug fixes.

## What an app package would mean

An application has a stable identity and revisions. Each revision describes its
entry point, files or assets, required service contracts, and access and
persistence requirements. Its build, validation, and deployment are work performed
on that revision. A user can reopen it and request a change to the same app.

Start with a small portable description and storage contract, then an adapter
that can run it. Reuse the existing store, services, gateways, and lifecycle
management where appropriate. An `app` package should earn its place by making
these contracts reusable across the CLI and Mu; another name for `service.Group`
or a generic container of metadata would not achieve that.

Keep three identities distinct:

- **App:** the software a person keeps using.
- **Revision:** the specific source and assets being checked or run.
- **Run:** an attempt to build, check, deploy, or invoke a revision.

A failed build must not replace a working revision. A retry must not create an
unrelated app or repeat an already completed external action unintentionally.
An output reference links a run to the app revision it produced. Reports, files,
and images can also be outputs; they should not have to pretend to be apps.

The app-building service owns generation and validation. A host owns execution
isolation, authentication, and deployment policy. Required capabilities in a
manifest describe access needs; they do not grant access. Generated code runs
under the host's policy, and services enforce the caller's identity.

## Prototype in Mu, extract into Go Micro

Mu already has an app service, saved output references, build jobs, and a work
layer that delivers results back to conversations. It also has product-specific
HTML rendering, account permissions, and delivery rules. Extract shared contracts
from that working path rather than moving the whole product into the framework.

The first implementation should exercise a complete path:

1. Ask for an app that uses registered services.
2. Create a stable app identity and a candidate revision; return a run reference.
3. Validate the candidate against real service contracts and check its behavior.
4. Save and run the successful revision; return an app reference someone can open.
5. Ask for a change; create a new revision of the same app.
6. Restart during the work and after completion; recover the status and saved app
   without resetting the attempt budget or publishing an incomplete revision.

Start with one supported application format and one runtime adapter. Mu's
service-backed HTML apps are a candidate, not a promise that the framework can
safely run arbitrary generated programs. Prove the contracts with the CLI and Mu
before naming or freezing exported Go interfaces.

## Go Micro and Mu

Go Micro is the reusable framework; Mu is an application runtime and product
built with it. The useful boundary is ownership, not repository count:

| Go Micro | Mu |
|----------|----|
| Service communication, discovery and storage interfaces | Concrete services and their data |
| Provider adapters and the common agent harness | Assistant instructions, model choices and product policy |
| Execution, checkpoint and workflow contracts | User-facing work lists and conversation delivery |
| A proven portable app/revision contract, if extracted | App authoring UI, rendering, account access and hosting |

A developer should be able to use Go Micro without adopting Mu's accounts,
conversation model, UI, or hosted services. Mu should be able to use the framework
without implementing equivalent provider loops or execution contracts. Mu's
product work records can project framework run state without replacing it.

An app service can remain in Mu while its reusable parts are identified. Extract
a package when another consumer, such as the CLI, can use it without Mu-specific
assumptions. Avoid placing an abstract app package in the framework merely to
mirror the product's nouns.

A monorepo with separate Go modules could simplify coordinated development, but
it would still need this dependency boundary and separate release contracts.
Combining everything into one module would make Go Micro a complete assistant
platform and require library users to adopt product concerns. That is a larger
product decision than this cleanup. For now, keep the repositories and remove
duplicated responsibilities through narrow, tested interfaces.

## What makes this v7

A credible v7 release has a coherent execution contract and a usable application
lifecycle, not merely a new package:

- Providers perform model turns; one agent harness owns tool execution and its
  streaming and recovery semantics.
- CLI chat and registered agents use that harness with explicitly configured tools.
- Defined workflows compose services and agents without duplicating their loops.
- Apps can be created, revised, run, and recovered through stable references.
- Mu consumes the shared contracts without maintaining an equivalent parallel layer.
- Existing service-only applications have a documented migration; core RPC,
  registry and broker contracts change only where a demonstrated need requires it.

The migration must cover direct v6 `Generate` callers that depend on automatic
tool execution, provider plugins, stored run formats, and cross-version service
communication. New run formats need versioned decoding or an explicit migration;
old state cannot silently be interpreted under new semantics.

The acceptance criterion is practical: **ask for useful software, use it, change
it, and keep it working after a restart**. The framework must also remain a good
way to write the same software directly in Go.
